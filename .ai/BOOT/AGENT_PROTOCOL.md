# AI Engineering OS: Agent Protocol

## Purpose
This document establishes the precise protocols for how AI agents identify themselves, communicate with each other, resolve conflicts, and collaborate efficiently within the Medivo Health Intelligence Platform repository. It ensures a seamless, traceable, and highly organized multi-agent workflow.

## Agent Identification Format
Transparency is critical when human developers and multiple AI agents interact within the same codebase. AI agents must explicitly declare their involvement in all generated artifacts.

### 1. Git Commits
Every git commit message generated or significantly influenced by an AI agent must include a specific trailer indicating AI authorship.
- **Format**: `Co-authored-by: Medivo AI OS <ai@medivo.health>`
- **Example**:
  ```
  feat(skin): implement biometric authentication for reports
  
  Adds FaceID/TouchID requirements before viewing sensitive AI Skin reports.
  
  Co-authored-by: Medivo AI OS <ai@medivo.health>
  ```

### 2. File Headers
When an AI agent creates an entirely new core file (e.g., a complex service, a critical architectural configuration), it should include a subtle header comment.
- **Format**: `// [AI-GEN] Generated by Medivo AI OS on [YYYY-MM-DD]`

### 3. Inline Code Comments
For highly complex algorithms, non-obvious workarounds, or critical architectural decisions generated by AI, an inline comment is required to explain the *reasoning*, not just what the code does.
- **Format**: `// [AI-REASONING]: Opted for a recursive CTE here to optimize the deep category tree traversal, preventing N+1 query issues.`

## Communication Protocol
AI agents do not communicate via direct messaging; they communicate asynchronously through persistent, shared markdown files located in the `.ai/MEMORY/` directory.

### Step-by-Step Procedure:
1. **Initialization**: Upon starting a task, the agent reads `SESSION_STATE.md` to understand the current objective.
2. **Execution**: The agent performs the necessary file reads and code modifications.
3. **Logging**: For every major milestone (e.g., "Completed API endpoint", "Fixed type errors"), the agent appends a brief, timestamped entry to `AGENT_LOG.md`.
4. **Knowledge Sharing**: If the agent discovers a codebase quirk (e.g., "The Redis client requires a specific timeout config"), it updates `KNOWLEDGE_GRAPH.md` so future agents are aware.
5. **Completion/Handoff**: Upon finishing a task or reaching a token limit, the agent finalizes the state and writes to `HANDOFF.md`.

## Detailed Handoff Procedures
When an agent's session is terminating (due to completion, error, or context limits), it MUST generate a `HANDOFF.md` file using the following exact template:

```markdown
# Agent Handoff: [Date] [Time]

## 1. Current Status
[Brief summary of what was successfully completed in this session. E.g., "Implemented the UI components for the Skin Report view and integrated the mock API."]

## 2. In-Progress Work
[What was currently being worked on when the session ended. E.g., "Currently writing unit tests for the ReportCard component. 2 of 5 tests are passing."]

## 3. Next Steps
[Explicit, actionable, numbered instructions for the next agent. E.g., 
1. Fix the failing test case regarding empty state rendering in ReportCard.
2. Connect the UI to the real trpc endpoint instead of the mock.]

## 4. Required Context
[List the absolute minimum files the next agent needs to load to continue smoothly. E.g., 
- `apps/customer-platform/components/ReportCard.tsx`
- `apps/customer-platform/__tests__/ReportCard.test.tsx`]

## 5. Open Questions / Blockers
[Any issues requiring human intervention or architectural decisions. E.g., "The design system lacks a token for the 'critical alert' color needed in the report. Please advise."]
```

## Conflict Resolution Decision Tree
When an AI agent encounters a conflict, it must follow this decision tree rather than guessing.

1. **Is it a Git Merge Conflict?**
   - **YES**: Is the conflict trivial (e.g., simple README additions)?
     - **YES**: Resolve automatically.
     - **NO**: Halt execution. Do NOT attempt to resolve complex code conflicts. Document the files in `HANDOFF.md` and notify the human user immediately.
   - **NO**: Proceed to step 2.

2. **Is it an Architectural Disagreement?** (e.g., User asks to bypass a domain boundary)
   - **YES**: The agent MUST explicitly warn the user, cite the `AI_CONSTITUTION.md` rule being violated, and propose a compliant alternative.
   - **Does the user insist on the violation?**
     - **YES**: Execute the user's command, but heavily document the deviation in `AGENT_LOG.md` and `KNOWLEDGE_GRAPH.md` as technical debt, tagging it with `[CONSTITUTION-VIOLATION]`.

3. **Is it a Linter/Compiler Conflict?**
   - **YES**: The generated code fails strict type checking or linting. The agent MUST NOT use `// @ts-ignore`. It must iteratively fix the types or refactor the code until it passes.

## Agent Capabilities Matrix
Different tasks require different agent profiles or specific prompts.

| Agent Profile | Primary Focus Area | Key Strengths | Typical Tasks |
| :--- | :--- | :--- | :--- |
| **Architect Agent** | System Design, DDD | High reasoning, context synthesis | Designing schemas, mapping domain boundaries, writing ADRs. |
| **Coder Agent** | Implementation | Speed, syntax accuracy | Building UI components, writing CRUD API endpoints, boilerplate generation. |
| **Refactor Agent** | Technical Debt | Large context window, pattern matching | Upgrading dependencies, codebase-wide renaming, structural reorganization. |
| **Reviewer Agent** | Quality Assurance | Skepticism, security focus | Auditing PRs, finding edge cases, enforcing Constitution rules. |
| **DBA Agent** | Data Persistence | SQL optimization, indexing | Writing complex migrations, optimizing slow queries. |
| **DevOps Agent** | Infrastructure | CI/CD, deployment | Configuring GitHub Actions, Dockerfiles, Terraform scripts. |
